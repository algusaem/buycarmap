# 0002 — pnpm

## Decided

pnpm 11. `pnpm-lock.yaml` is the lockfile, and `/package-lock.json` is
**gitignored specifically to stop npm re-creating it**.

Dependency build scripts are blocked by default; packages allowed to run them are
allowlisted in `pnpm-workspace.yaml` under `onlyBuiltDependencies` — currently
prisma, `@prisma/engines`, msw, sharp and `unrs-resolver`.

## What it beat

npm, which the project started on. The switch was made deliberately
(`chore: standardize on pnpm and fix the dependency toolchain`), not drifted
into.

The deciding factor was **two lockfiles producing two different trees.** With
both present, `npm install` and `pnpm install` resolve differently, and a bug
that reproduces for one person and not another costs more than any install-speed
difference. Picking one and making the other impossible was the point; pnpm's
disk sharing and stricter `node_modules` layout were the tiebreakers.

The strict layout has a real benefit worth naming: pnpm does not flatten
transitive dependencies into the top level, so a package cannot import something
it never declared. That class of accidental dependency simply cannot compile.

## What it costs

**`ERR_PNPM_IGNORED_BUILDS` is a papercut that reads like a failure.** Any
dependency with a native or postinstall step is silently skipped until it is
added to `onlyBuiltDependencies`, and the resulting breakage usually surfaces
somewhere unrelated.

That default is right — arbitrary install-time code execution is a real supply
chain risk — but it means a new native dependency always costs one confusing
install.

## What would change our mind

- Moving to a monorepo tool that assumes a different package manager.
- A deployment target that cannot run pnpm without a shim. Vercel supports it
  natively, so this is hypothetical.

Nothing about install speed alone would.
